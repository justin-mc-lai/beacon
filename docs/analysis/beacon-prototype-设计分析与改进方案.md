# Beacon Prototype 设计分析与改进方案

**分析日期**: 2026-04-20  
**当前版本**: v1.3.6  
**文档状态**: 深度分析与改进建议

---

## 一、问题诊断

### 1.1 当前 Prototype 系统的核心问题

通过对现有代码和输出的分析，发现以下关键问题：

#### 问题 1：技术实现细节泄漏到产品语言层

**现象：**
```markdown
# 当前输出示例
- 页面职责：展示项目数、阻塞数、当前交付和介入点
- 关键模块：经营总览条、重点介入区、项目推进摘要
- 用户动作：点击项目组合入口 -> management-overview
```

**问题：**
- `management-overview` 是技术层的 page_id，不是业务语言
- "经营总览条"、"重点介入区" 是 UI 组件名称，不是用户目标
- 缺少业务场景和用户意图的描述

#### 问题 2：线框图过于抽象，缺乏业务语义

**现象：**
```text
+------------------------------------------------------+
| 经营总览条 | 活跃项目 | 阻塞项目 | 活跃 runtime |
+------------------------------------------------------+
| 重点介入区                                      |
+------------------------------------------------------+
```

**问题：**
- ASCII 图只展示了布局结构，没有业务含义
- "活跃 runtime" 是技术术语，用户看不懂
- 缺少数据来源、业务规则、异常处理的说明

#### 问题 3：页面定义混杂技术标识符

**现象：**
```python
PAGE_CATALOG = {
    "home": {  # 技术 ID
        "name": "首页",  # 业务名称
        "actions": [
            {"target": "management-overview"}  # 技术路由 ID
        ]
    }
}
```

**问题：**
- `"home"`, `"management-overview"` 是技术层的 page_id
- 用户看到的应该是 "经营驾驶舱首页" → "管理总览"
- 技术标识符不应该出现在产品文档中

#### 问题 4：缺少业务场景和用户意图

**现象：**
当前输出只描述 "有什么"，不描述 "为什么" 和 "怎么用"：
```markdown
- 页面职责：展示项目数、阻塞数
- 关键模块：经营总览条、重点介入区
```

**问题：**
- 没有说明用户在什么场景下需要这个页面
- 没有说明用户的目标是什么
- 没有说明数据如何帮助用户做决策

## 二、根本原因分析

### 2.1 架构层次混淆

当前系统存在三个层次的混淆：

```
┌─────────────────────────────────────┐
│ 业务语义层 (Business Semantics)     │  ← 用户看到的
│ - 经营驾驶舱                         │
│ - 项目健康度                         │
│ - 介入建议                           │
└─────────────────────────────────────┘
           ↓ 应该隔离 ↓
┌─────────────────────────────────────┐
│ 产品设计层 (Product Design)         │  ← 产品经理定义的
│ - 页面结构                           │
│ - 交互流程                           │
│ - 信息架构                           │
└─────────────────────────────────────┘
           ↓ 应该隔离 ↓
┌─────────────────────────────────────┐
│ 技术实现层 (Technical Implementation)│  ← 开发者实现的
│ - page_id: "home"                   │
│ - route: "/management-overview"     │
│ - component: "ProjectCard"          │
└─────────────────────────────────────┘
```

**当前问题：** 三层混在一起，技术术语泄漏到业务层。

### 2.2 缺少业务语义模型

当前 `PAGE_CATALOG` 直接定义技术结构，缺少业务语义抽象：

```python
# 当前：技术优先
PAGE_CATALOG = {
    "home": {  # 技术 ID
        "sections": ["经营总览条", "重点介入区"],  # UI 组件名
        "actions": [{"target": "management-overview"}]  # 技术路由
    }
}

# 应该：业务优先
BUSINESS_SCENARIOS = {
    "经营决策场景": {
        "用户角色": "项目管理者",
        "核心目标": "快速判断当前经营状态，识别需要介入的项目",
        "关键问题": [
            "有多少项目在推进？",
            "哪些项目有风险？",
            "我应该优先关注什么？"
        ],
        "决策支持": {
            "项目健康度总览": "一眼看出整体状况",
            "风险项目列表": "快速定位问题",
            "介入建议": "明确下一步行动"
        }
    }
}
```

## 三、设计原则

### 3.1 业务语义优先原则

**原则：** 所有用户可见的内容必须使用业务语言，禁止技术术语。

**实施规则：**
1. 页面名称：使用业务场景名称，不使用技术 ID
   - ✅ "经营驾驶舱首页"
   - ❌ "home"
   
2. 功能描述：使用用户目标，不使用技术实现
   - ✅ "帮助管理者快速识别需要介入的项目"
   - ❌ "展示项目数、阻塞数"
   
3. 交互说明：使用业务动作，不使用技术操作
   - ✅ "查看项目详细健康报告"
   - ❌ "点击进入 project-detail 页面"

### 3.2 场景驱动设计原则

**原则：** 从用户场景出发，而不是从技术结构出发。

**设计流程：**
```
1. 识别用户角色 → 2. 定义使用场景 → 3. 明确用户目标 → 4. 设计信息架构 → 5. 生成线框图
```

**示例：**
```yaml
场景: 项目管理者早晨打开系统
角色: 项目管理者
目标: 快速了解今天需要关注什么
关键问题:
  - 有哪些项目需要我介入？
  - 哪些项目有风险？
  - 今天的优先级是什么？
信息需求:
  - 项目健康度总览
  - 风险项目列表（按紧急程度排序）
  - 今日建议行动
```

### 3.3 分层隔离原则

**原则：** 业务层、产品层、技术层严格分离。

**实施方案：**
```python
# 业务语义层 (business_semantics.py)
BUSINESS_SCENARIOS = {
    "经营决策": {...},
    "项目诊断": {...},
}

# 产品设计层 (product_design.py)
WIREFRAME_TEMPLATES = {
    "经营驾驶舱": {
        "layout": "dashboard",
        "sections": [...],
    }
}

# 技术映射层 (technical_mapping.py)
PAGE_ROUTING = {
    "经营驾驶舱": {
        "page_id": "home",
        "route": "/",
        "component": "DashboardHome"
    }
}
```

### 4.2 线框图生成逻辑改进

**改进前：**
```python
def generate_wireframe(page_id: str):
    page = PAGE_CATALOG[page_id]
    wireframe = f"# {page['name']}\n"
    wireframe += f"职责: {page['responsibility']}\n"
    # 直接输出技术结构
```

**改进后：**
```python
def generate_business_wireframe(scenario_name: str):
    scenario = BUSINESS_SEMANTIC_MODEL[scenario_name]
    
    # 1. 场景说明
    wireframe = f"# {scenario['meta']['场景名称']}\n\n"
    wireframe += f"## 使用场景\n"
    wireframe += f"**用户角色：** {scenario['meta']['用户角色']}\n"
    wireframe += f"**使用时机：** {scenario['meta']['使用时机']}\n\n"
    
    # 2. 用户目标
    wireframe += f"## 用户目标\n"
    wireframe += f"{scenario['用户目标']['主要目标']}\n\n"
    
    # 3. 关键问题
    wireframe += f"## 这个页面帮助用户回答的问题\n"
    for question in scenario['关键问题']:
        wireframe += f"- {question}\n"
    
    # 4. 信息架构（业务语言）
    wireframe += f"\n## 页面信息架构\n\n"
    for section_name, section_data in scenario['信息架构'].items():
        wireframe += f"### {section_name}\n"
        wireframe += f"**业务价值：** {section_data['业务价值']}\n\n"
        
        # 生成业务语义线框图
        wireframe += generate_semantic_wireframe_section(section_name, section_data)
    
    # 5. 用户动作（业务语言）
    wireframe += f"\n## 用户可以做什么\n"
    for action in scenario['用户动作']:
        wireframe += f"- **{action['动作']}**\n"
        wireframe += f"  - 触发方式：{action['触发条件']}\n"
        wireframe += f"  - 进入场景：{action['目标场景']}\n"
    
    return wireframe

def generate_semantic_wireframe_section(section_name: str, section_data: dict) -> str:
    """生成带业务语义的线框图区块"""
    wireframe = "```\n"
    wireframe += f"┌─ {section_name} ─────────────────────────────────┐\n"
    wireframe += f"│                                                  │\n"
    
    if "关键指标" in section_data:
        for indicator in section_data['关键指标']:
            wireframe += f"│  {indicator['指标']}: [数值]                    │\n"
            wireframe += f"│  ({indicator['说明']})                          │\n"
    
    if "展示内容" in section_data:
        wireframe += f"│                                                  │\n"
        wireframe += f"│  展示内容：                                      │\n"
        for content in section_data['展示内容']:
            wireframe += f"│  - {content}                                    │\n"
    
    wireframe += f"│                                                  │\n"
    wireframe += f"└──────────────────────────────────────────────────┘\n"
    wireframe += "```\n\n"
    
    # 添加数据说明
    if "数据来源" in section_data:
        wireframe += f"**数据来源：** {section_data['数据来源']}\n"
    if "更新频率" in section_data:
        wireframe += f"**更新频率：** {section_data['更新频率']}\n"
    
    wireframe += "\n"
    return wireframe
```

## 七、预期效果

### 7.1 产品文档质量提升

**改进前：**
- 技术术语混杂，产品经理难以理解
- 缺少业务场景，开发者不理解为什么要做
- 线框图抽象，设计师无法直接使用

**改进后：**
- 纯业务语言，产品经理可以直接审阅
- 明确业务场景，开发者理解业务价值
- 线框图包含业务语义，设计师可以直接转化为高保真设计

### 7.2 需求传递效率提升

**改进前：**
```
PRD → 技术线框图 → 产品经理翻译 → 设计师理解 → 开发者实现
      ↑ 信息损失      ↑ 理解偏差      ↑ 实现偏差
```

**改进后：**
```
PRD → 业务语义线框图 → 设计师/开发者直接理解并实现
      ↑ 信息完整        ↑ 理解一致
```

### 7.3 跨角色协作改善

| 角色 | 改进前的痛点 | 改进后的收益 |
|------|-------------|-------------|
| 产品经理 | 看到技术术语，需要翻译 | 直接看到业务语言，可以直接审阅 |
| 设计师 | 线框图太抽象，需要猜测业务含义 | 线框图包含业务语义，可以直接设计 |
| 开发者 | 不理解为什么要做，只知道做什么 | 理解业务场景和价值，可以提出更好的实现方案 |
| QA | 不知道如何验证业务价值 | 明确业务目标，可以设计更好的测试用例 |

## 八、总结

### 8.1 核心改进

1. **业务语义优先：** 所有用户可见内容使用业务语言
2. **场景驱动设计：** 从用户场景出发，而不是技术结构
3. **分层隔离：** 业务层、产品层、技术层严格分离
4. **信息完整性：** 包含业务价值、数据来源、异常处理

### 8.2 关键原则

- **禁止技术术语泄漏到业务层**
- **线框图必须包含业务语义**
- **明确用户场景和目标**
- **说明业务价值和决策支持**

1. 评审本方案，确认设计方向
2. 按照实施路径逐步推进
