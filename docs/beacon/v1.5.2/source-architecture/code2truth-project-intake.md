# Source Architecture: code2truth-project-intake

- version: `v1.5.2`
- feature: `code2truth-project-intake`

## Runtime Placement

The feature enters as a support/intake surface before formal truth promotion. It composes existing Beacon source-driven analysis, lighthouse/source-architecture projections, truth-map resolver, feature package validation, implement planning, doctor governance verification, and QA.

It may later expose a `code2truth` or `project-intake` command/skill, but the long-lived authority remains the resolver-selected feature package.

## Write Path

Candidate outputs are written as support research and evidence refs first. After user confirmation, accepted material is promoted into:

- `docs/beacon/v1.5.2/features/<slug>/truth.md`
- `docs/beacon/v1.5.2/features/<slug>/tests.md`
- `docs/beacon/v1.5.2/features/<slug>/tasks.md`
- `docs/beacon/v1.5.2/features/<slug>/evidence.md`

Generated JSON, provider graphs, and runtime records are projections/evidence only.

## Read Models And Projections

Read-side inputs can include Beacon lighthouse maps, source architecture docs, tests, CLI behavior, skill files, and local provider artifacts such as `.understand-anything/knowledge-graph.json`.

The authoritative read model for downstream implement/QA remains truth-map resolved package Markdown.

## Contract Boundaries

In scope:

- source inventory and candidate truth reconstruction;
- provider evidence classification;
- user-confirmed promotion into package truth;
- implement no-op/evidence-only admission;
- QA coverage for package truth, evidence, governance, and existing behavior.

Out of scope:

- treating code or provider graphs as direct truth;
- bypassing user confirmation, requirement clarity, or freeze;
- forcing source edits when existing behavior already satisfies frozen truth.
