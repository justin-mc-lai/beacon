# Research: Beacon Truth Map Center and Package Cutover v1.5.2

v1.5.2 carries forward the accepted v1.5.1 resolver-center direction and completes the authoritative package cutover.

The important correction is that Beacon must not replace one multi-write truth system with another. The target is a single Markdown truth package, resolved by CLI code, with optional generated evidence.

## v1.5.2 Capability Convergence

### Target Shape

v1.5.2 is not another compatibility layer. It is the policy flip that makes:

```text
truth-map resolver -> features/<slug>/{truth,tests,tasks,evidence}.md
```

the normal Beacon truth production and consumption path.

Legacy `prd/`, `user-story/`, and `qa/test-cases/` may remain on disk, but they must stop acting as normal truth authority. Their allowed roles are limited to:

- `doctor` rebuild target from package truth
- `change` absorb source into package truth
- historical/archive evidence

### What v1.5.1 Already Gives v1.5.2

- `beacon.utils.truth_map` exists as the resolver center.
- Resolver can locate feature package surfaces.
- Resolver can classify machine JSON as generated state, not truth.
- Version governance surfaces are separated from generated governance state.
- High-risk truth entrypoints are inventoried.
- v1.5.1 acceptance already made exceptions visible instead of pretending everything was migrated.

### What v1.5.2 Must Add

- Runtime policy must return `feature_package_authoritative`, not `feature_package_authoritative_ready`, for v1.5.2+.
- Entry point inventory must stop accepting `v1.5.1_legacy_exception` as a pass state for normal truth producers/consumers.
- Material audit must treat package surfaces as the completeness source. It must not require legacy `canonical_refs` targets to exist before package truth is considered complete.
- Gate, QA, release, and status must consume package-derived parser output through resolver APIs.
- PRD/user-story/test-case command surfaces must become package writers or compatibility adapters, not independent truth writers.
- Doctor rebuild and change absorb routes must be explicit, deterministic, and fail closed.
- Skills must instruct LLMs to read and write the package truth model first; old triptych wording must be marked rebuild/absorb-only for v1.5.2.

## Cutover Decision Points

### 1. Authority Policy

The resolver should be version-aware:

- v1.5.1: `feature_package_authoritative_ready`
- v1.5.2+: `feature_package_authoritative`

This avoids a global hard-coded authority flip that would rewrite old version semantics.

### 2. Legacy Surface Boundary

v1.5.2 should not delete old files as part of the cutover. Deletion creates unnecessary migration risk. The stronger and safer rule is:

- old files can exist
- old files can be rebuilt
- old files can be absorbed
- old files cannot win authority against package truth

If legacy content disagrees with package truth, the gate result should be drift/fail-closed with package truth as winner.

### 3. JSON Boundary

The target is Markdown-first, not Markdown-plus-required-JSON. JSON is allowed only when it is:

- generated by resolver or runtime
- labeled as generated state
- source-hash traceable when it claims to mirror package Markdown
- never required as a twin for package truth validity

Release and QA must not block because a package Markdown truth document has no JSON twin.

### 4. Skill Boundary

LLM skills should stop teaching the old main chain as the normal truth chain for v1.5.2. The expected guidance should be:

```text
read resolver -> read feature package -> write package draft/checklist where allowed -> let CLI validate/state-advance
```

The LLM may write Markdown content. It must not directly advance state or treat generated JSON as truth.

## High-Risk Entry Points To Retire From Legacy Authority

These surfaces are high risk because they either read requirement truth, write requirement truth, or gate delivery:

- `beacon/commands/prd.py`
- `beacon/commands/user_story.py`
- `beacon/commands/test_case.py`
- `beacon/commands/workflow.py`
- `beacon/commands/truth.py`
- `beacon/commands/gate.py`
- `beacon/commands/release.py`
- `beacon/utils/prd_bootstrap.py`
- `beacon/utils/requirement_clarity.py`
- `beacon/utils/requirement_deepening.py`
- `beacon/utils/material_audit.py`
- `beacon/utils/manifest.py`
- `beacon/utils/acceptance_kit.py`
- packaged `skills/beacon/**/SKILL.md`
- installed/project `.agents/skills/**/SKILL.md`

v1.5.1 could pass while these were explicit exceptions. v1.5.2 should not.

## Acceptance Focus

The v1.5.2 QA bar should prove:

- package Markdown is authoritative without JSON twins
- all normal truth consumers resolve through truth-map APIs
- old triptych files cannot satisfy package completeness by themselves
- old triptych drift is reported and cannot override package truth
- doctor rebuild and change absorb are the only sanctioned legacy routes
- material-audit, gate, QA, release, and status all agree on the same authority model
- skills no longer instruct LLMs to treat PRD/user-story/test-case as the normal v1.5.2 truth chain

## Brainstorm Verdict

The direction is valid, but v1.5.2 should be treated as a real cutover release, not a small policy rename. The minimum safe scope is:

1. version-aware authority policy in resolver
2. package-first completeness and gate input resolution
3. legacy triptych demotion to rebuild/absorb-only
4. JSON generated-state enforcement
5. skill guidance refresh
6. v1.5.2-specific tests proving old truth cannot win

The recommended next route is `beacon-test-case` before implementation, because the biggest remaining uncertainty is not product intent; it is whether every dangerous consumption path has a concrete failing test.
