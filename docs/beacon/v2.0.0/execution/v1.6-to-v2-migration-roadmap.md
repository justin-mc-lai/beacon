## 4. 六大迁移风险

### 风险 1：Markdown-as-Truth 解析行为必须字节级一致

Python 的 `re` / 手写解析与 Rust 的 `pulldown-cmark` / `serde` 行为会有微妙差异（空白处理、Unicode、CJK 标点）。v2 TC-007 强制 MD 是唯一真相权威。

**缓解**：P1 阶段建立 golden fixture 对——Python 解析器生成 reference JSON，Rust 解析器必须对同一 Markdown 产生相同 JSON。

### 风险 2：150+ Gate Reason Codes 字节级兼容

TC-039 明确要求 reason_codes 与 v1 字节级兼容。

**缓解**：P1 阶段将 reason codes 提取为 `beacon-core` Rust enum，每个变体 `#[serde(rename = "v1_reason_code_string")]`。生成 regression fixture。

### 风险 3：子进程→进程内调用模型变更

v1.6 通过 subprocess 编排子命令提供进程隔离。v2 Rust 倾向进程内直接调用。

**缓解**：保持每个子命令同时可作为独立进程入口和库函数调用。P6 E2E 双路径覆盖。

### 风险 4：全局 SQLite vs 散装 JSON 迁移

v1.6 运行时状态散布在 291+ 文件中。v2 收束到 `~/.beacon/beacon.db`。TC-039/056/016 要求：lifecycle_events 保留、迁移 <60s、双写 fail-closed。

**缓解**：P3 实现严格双写检测。`BEACON_V2=1` 为切换开关。

### 风险 5：33 Skills PyO3 路由完整性

TC-059 要求 Python shim 通过 doctor verify-context。33 skills 全量回归（不是抽样）。

**缓解**：P4 阶段 `beacon-python` 每个 PyO3 函数走 Rust 或 fallback Python。`BEACON_V2=1` 控制。

### 风险 6：beacon-loop / beacon-run 吸收

v2 orchestrator 要吸收 TS 双子项目。v1.6 侧 `beacon-loop-native-runner` 还有 17/41 task blocked。

**缓解**：v2 P2 先用 SubprocessBackend 桥接 `beacon-run` 二进制，逐步替换。

## 7. 不变合约（v2 必须遵守的 10 条铁律）

来源：`docs/beacon/global-boundaries.md`

1. **主链不可膨胀**：`plan→truth→generate→evaluate→release`，支持面不能升级为主链阶段
2. **真相/验收/gate 标准不因运行时模式、宿主差异、内部协作形式而改变**
3. **复杂性由机器侧吸收**，不转嫁为人类认知负担
4. **单真相源 + 单向投影 + 事务一致**：MD 是 canonical，JSON/SQLite 是 projection，漂移 fail-closed
5. **Skill 定义决策边界**，不是 step-by-step 脚本
6. **强 gate / fail-closed 例外**：qa、release、freeze、安全/权限/合规允许写顺序/事务/验证/回滚要求
7. **学习影响判断和排序，但不直接定义 truth 或 gate verdict**
8. **默认行为**：显式假设管理、简洁优先、手术式变更、目标驱动验证
9. **人类面最小可操作，机器面完整可审计**
10. **外部能力只能作为研究或受治理输入，不能升级为默认前提**

## 8. 两条基线并行策略

```
主线 (beacon/v1.6.0)              Worktree (worktree-v2-migration-plan)
├─ v1.6.x 稳定迭代                 ├─ v2 迁移规划文档
├─ 需求真相质量治理 (见 companion doc) ├─ P1..P6 逐步实现
├─ TIG 完善 + QA                   ├─ golden fixture 对
├─ native-runner unblock           ├─ reason_codes 字典
└─ v1.6.0 release                  └─ 定期 merge 主线变更
```

- 主线保持生产可用，所有 v1.6.x 修复和增强走主线
- Worktree 做迁移规划和 v2 早期开发，定期从主线 merge 保持同步
- v2 各 Phase 在 worktree 中完成后，逐 Phase 合入主线
