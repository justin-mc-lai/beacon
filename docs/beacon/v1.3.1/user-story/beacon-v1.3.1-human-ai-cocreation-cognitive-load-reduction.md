# 用户故事：Beacon v1.3.1 人机共创心智包袱减重

**Feature**: `beacon-v1.3.1-human-ai-cocreation-cognitive-load-reduction`  
**Version**: `v1.3.1`  
**Date**: `2026-04-12`  
**Status**: `planning line`

## US-001：作为 Beacon 人类使用者，我希望只面对有限主闭环，而不是越来越多的命令面

**验收标准**：

- Beacon 人类主闭环必须收敛为 `prd -> user-story -> test-case -> implement -> qa -> release`
- 这 6 个阶段必须成为人类主交付心智面
- 其他 machine lanes 不应成为默认主入口

## US-002：作为需求作者，我希望 `brainstorm` 在 `prd -> user-story` 探索中持续存在，但不增加额外操作负担

**验收标准**：

- `brainstorm` 必须持续为 `prd` 与 `user-story` 提供需求发散与闭环能力
- 人类不应被迫把 `brainstorm` 当成长期额外主阶段记忆
- `prd` / `user-story` 正式产物必须体现 brainstorm 后的业务收敛结果

## US-003：作为实现负责人，我希望 `implement` 对人类保持单入口，但内部可由 Beacon 自由使用 team 协作闭环交付

**验收标准**：

- 对人类暴露的主入口仍应是 `implement`
- 机器内部可继续使用 team 多代理实现快速编码闭环
- 最终交付必须严格对齐冻结的人类需求文档

## US-004：作为 QA 负责人，我希望 `qa` 对人类保持单入口，但内部能使用 team、learning、auto research 提升覆盖与边界清晰度

**验收标准**：

- 对人类暴露的主入口仍应是 `qa`
- Beacon 内部可使用 team、多轮 learning、auto research
- 每一轮 QA 都必须比上一轮带来新的发现、覆盖补充或边界澄清
- 这些动作必须围绕冻结用户故事展开

## US-005：作为旧项目操作者，我希望 Beacon 源码升级后，可以按文档版本一键同步旧物料

**验收标准**：

- 必须支持按指定 `docs version` 更新旧的 `.machine/user-story`、`.machine/qa` 等物料
- 操作者不应手工重建这些 machine materials
- 同步动作必须显式、可审计、可重复

## US-006：作为 Beacon 人类使用者，我希望探索极简 CLI，而不是记忆一大串细分命令

**验收标准**：

- `v1.3.1` 必须探索人类极简命令行
- 极简 CLI 的核心目标是服务六段闭环，而不是暴露更多底层能力
- help/status/doctor 可以在必要时揭示复杂度，但不应成为人类长期主心智

## US-007：作为产品负责人，我希望人类交付与机器协作分层明确

**验收标准**：

- 人类只需确保对齐正式文档交付
- 机器协作入口与运行细节可由 Beacon 自由制定
- 机器不得脱离冻结的人类文档自行扩展需求边界

## US-008：作为需求负责人，我希望需求文档里的遗漏点、不清晰点、问号点、未澄清点都被显式审核，否则不能冻结

**验收标准**：

- Beacon 必须把遗漏点、不清晰点、问号点、未澄清点、需求不明点视为冻结阻塞项
- `prd` / `user-story` 在存在上述问题时不得 freeze
- 人类必须先完成需求审核与澄清闭环

## US-009：作为技术负责人，我希望每个版本在实现前都先完成技术评审，给出确定性实现面

**验收标准**：

- 每个版本的技术评审必须明确：
  - git 分支
  - worktree 是否启用
  - 隔离开发环境
  - 具体实现服务目录
- 若是 monorepo / multi-service 项目，必须明确服务边界与责任归属
- 未完成上述技术评审，不得进入正式实现

## US-010：作为多服务项目操作者，我希望类似 rolo 这类项目能在版本评审阶段就明确具体改哪些服务

**验收标准**：

- 技术评审必须给出具体服务列表，而不是只写抽象模块名
- 必须区分：
  - 网关 / BFF
  - 下游服务
  - 只读参考服务
- 必须把这些信息纳入版本实现面材料
