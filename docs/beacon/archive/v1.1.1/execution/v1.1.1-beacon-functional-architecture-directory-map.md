# Beacon v1.1.1 整体功能架构映射与需求目录文件地图

> 目的：给出 Beacon 的 **功能架构 → 命令模块 → 需求产物目录 → 运行态状态文件** 的统一映射，并明确 `docs/beacon` / `docs/product` 的目标口径与当前实现差异。

## 1. 结论先行

### 1.1 Canonical 口径（本轮确认）

Beacon skill 项目的统一口径应为：

1. **`docs/beacon/<version>/` 是唯一维护的信息源（source/meta）**
2. **`docs/product/<version>/` 只是旧 skill / 历史 PTK 的兼容视图**
3. **`docs/product/` 不应再作为人工维护目录**
4. **兼容修复 / 迁移入口应归属 `beacon doctor`**
5. **运行态状态、证据与闭环仍落在 `.beacon/`**

> 换句话说：后续所有 Beacon 新文档，应先写 `docs/beacon`，而不是双目录人工维护。

### 1.2 当前实现现状（尚未完全对齐）

当前仓库与实现仍存在以下未收敛点：

- `README.md` 已基本表达“`docs/beacon` 为主、`docs/product` 为兼容”
- 核心命令仍存在 **双写 `docs/beacon + docs/product`** 的实现
- 多数分析/设计类命令仍默认写入 `docs/product`
- `beacon/utils/context_files.py` 仍把 `docs/product` 表述为 user-facing tree
- `beacon doctor` 当前只负责 context block setup/verify，**尚未真正执行 docs 迁移/修复**

因此当前准确表述应为：

> **目标口径已经明确为 `docs/beacon` 单一维护源；但当前实现仍保留历史双树兼容行为，尚未完全收敛。**

## 2. Beacon 整体功能架构分层

| 层级 | 作用 | 代表模块/命令 | 主要输出 |
|---|---|---|---|
| L1 入口与路由层 | 自然语言入口、意图识别、边界判断 | `ask`, `prompt`, `intent_router.py` | 命令计划、边界建议、路由结果 |
| L2 需求产物层 | 产出 think / user-story / prd / test-case / version 等核心文档 | `think.py`, `user_story.py`, `prd.py`, `test_case.py`, `version.py` | 版本化需求文档 |
| L3 工作流编排层 | 串联 think→...→gate 主链，组织 handoff/repair | `workflow.py`, `run.py`, `resume.py` | workflow 状态、execution 工件 |
| L4 治理与放行层 | gate / release / report / team | `gate.py`, `release.py`, `report.py`, `team.py` | execution/release 工件 + `.beacon` 治理状态 |
| L5 分析与产品方法层 | analyze、design、roadmap、api-design、kano 等 | `analyze.py`, `design.py`, `roadmap.py`, `api_design.py` 等 | 辅助产品文档 / 研究材料 |
| L6 记忆与闭环层 | memory、feedback、save/recall/status | `memory.py`, `feedback.py`, `remember.py`, `recall.py` | `.beacon/memory/*`、生命周期状态 |
| L7 环境与上下文层 | doctor / init / context / compat | `doctor.py`, `init.py`, `context_files.py` | 上下文块、诊断报告、兼容修复入口 |

## 3. 需求目录与文件地图（目标模型）

### 3.1 `docs/beacon/<version>/` —— 唯一维护源

该目录承担：

- Beacon 版本化需求材料的唯一事实源
- workflow / gate / evidence / release / execution 的治理视图
- 研究、架构蓝图、repair 契约、版本演进文档

典型子目录：

```text
docs/beacon/<version>/
├── think/
├── user-story/
├── prd/
├── qa/test-cases/
├── execution/
├── release/
├── version/
└── research/
```

### 3.2 `docs/product/<version>/` —— 兼容视图

该目录只应承担：

- 历史 PTK / 旧 skill 的读取兼容
- 已迁移项目的过渡视图
- doctor 未来执行 repair / migration 时的目标兼容树

**约束：**

- 不再作为人工维护源
- 不应在新版本规划中手工同步编辑
- 若存在内容，应视为兼容副本，而不是 source/meta

### 3.3 `.beacon/` —— 运行态与证据链

```text
.beacon/
├── state/
├── memory/
├── runs/
├── handoffs/
├── gate-report.json
├── auto-test-status.json
└── evidence-manifest.json
```

## 5. Worktree repair 对目录治理的约束

针对 v1.1.1 的 worktree repair 演进，目录约束应增加：

1. repair / team-fix 契约只在 `docs/beacon/<version>/execution/` 维护
2. repair 分支、base branch、target branch、worktree path 等元信息只以 `docs/beacon` 文档为准
3. 旧 skill 若仍读取 `docs/product`，应依赖 doctor 提供的 compat repair / migration，而不是手工再写一份
4. 外部执行器（OMC / OMX / team / swarm）消费的也是 Beacon 文档契约，不改变 Beacon 的目录主从关系

---

## 6. 收敛建议（从当前实现走向目标口径）

建议按三步收敛：

1. **文档口径先统一**
   - README、version/execution 文档统一声明：`docs/beacon` 是唯一维护源
2. **doctor 承接 compat repair/migration**
   - 新增 `docs/product -> docs/beacon` 迁移、缺失补齐、兼容镜像修复能力
3. **命令写路径收敛**
   - 核心命令改为先写 `docs/beacon`
   - `docs/product` 仅在 compat mode / doctor repair 下生成

---

## 7. 本轮确认结论

本轮对外口径应明确为：

> **Beacon skill 项目统一只维护 `docs/beacon` 作为信息源 meta；`docs/product` 仅为兼容旧 skill 的过渡目录，目标由 `beacon doctor` 负责修复与迁移。**

同时应补充一句现实说明：

> **当前代码尚未完全对齐该口径，仍存在双写与旧路径默认输出，需要后续版本继续收敛。**
