# Execution Boundaries (v1.4.7)

## Core Rule

Beacon stays lightweight by keeping authority narrow even when support capability expands.

## Mainline

The public mainline remains:

`prd -> user-story -> test-case -> implement -> qa -> release`

`prototype` remains conditional.

## Support Surface Boundaries

Support skills may:

- challenge
- converge
- diagnose
- strengthen evidence
- improve context and execution quality

Support skills may not:

- become canonical truth by default
- issue release verdicts by default
- silently replace `change`, `implement`, `qa`, or `release`
- invent a new lifecycle stage

## Automation Boundaries

Automation may:

- manage bounded closure-state
- preserve active issue inheritance
- guard queue revision and single-flight execution
- surface promotion-proof signals

Automation may not:

- silently rewrite truth
- auto-run deep/refreeze/release end to end
- continue across truth barriers without refreeze
- convert blocked gate evidence into pass

## Default Behavior Boundary

Default behavior must preserve these four lightweight principles:

1. explicit assumptions and ambiguity management
2. simple-first decisions
3. surgical changes
4. goal-driven verification closure
