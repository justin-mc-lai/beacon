# Boundaries (v1.1.12)

## In scope

- single-source version truth for skill / runtime / docs current-line resolution
- profile-aware navigator and stage-local execution routing
- design brief compilation
- design-system contract compilation
- guideline audit artifacts
- bounded autoresearch iteration surfaces
- typed learning-plane policy surfaces
- capability-bounded project execution adapters
- takeover baseline gates before implementation expansion
- read-only project profile / service-slice / contract inputs
- freeze/gate consumption of design-governance artifacts
- implement branch preflight and exact version branch enforcement

## Out of scope

- turning Beacon core into a general shell orchestration runtime
- copying project-specific gateway / UAT / pipeline implementations into Beacon core
- full design-canvas editing
- unrestricted frontend self-modification
- learning-plane mutation of project execution commands, secrets, cookies, or storage state
- pixel-perfect visual diff infrastructure
- replacing human design judgement everywhere
- rewriting takeover current-state truth through autoresearch

## Boundary layers

1. Requirement kernel
2. Delivery evidence kernel
3. Project execution adapters
4. Learning plane

Layer rules:

- Layer 1 and Layer 2 are Beacon core
- Layer 3 remains project-specific and external-facing
- Layer 4 may only optimize policy / compiler / evaluation surfaces

## Hard boundaries

1. skill / runtime / release docs may not disagree on current version truth without an explicit machine-readable planning/runtime split
2. navigator must resolve project mode and profile binding before recommending native implementation paths
3. project skill orchestration may not run if capability / stage / evidence contracts do not match the requested stage
4. autoresearch may not directly widen into arbitrary HTML/CSS rewrite loops
5. autoresearch may not optimize project execution commands, gateway/UAT/pipeline actions, secrets, or takeover current-state truth
6. design finding writeback must target bounded policy surfaces first
7. guideline review cannot be treated as optional if design governance is enabled
8. takeover projects may not enter `implement` before current-state architecture/service-map/refactor-boundary baseline is frozen
9. older non-governed prototype lines must stay compatible
10. implement may not start coding on `main`, detached HEAD, or non-`beacon/<version>` branches
