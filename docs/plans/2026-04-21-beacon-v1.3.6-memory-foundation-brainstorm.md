# Beacon v1.3.6 记忆基座改造头暴

**Date**: 2026-04-21  
**Version**: v1.3.6（planning line）  
**Status**: Brainstorm Draft

---

## 1. What We're Building

Beacon 需要一层更强的记忆基座，但这层基座不是为了把 Beacon 变成通用个人知识脑，而是为了服务它最核心的人机协作场景：

- 需求冻结
- 交付接力
- QA 追溯
- release 证据闭环

这次改造的目标是让 Beacon 在 `prd -> user-story -> test-case -> prototype -> implement -> qa -> release` 主链中，能够稳定保存原始证据、构建跨阶段关联、按上下文分层召回，并把“为什么给出这个判断”明确回链到 artifact 与 evidence。

---

## 2. 方案比较

### 方案 A：继续沿用 summary-first memory，小修 recall

描述：
只在当前 `memory-v1.json + workflow-lifecycle + friction evolution` 上补搜索和字段。

**Pros**
- 改动最小
- 兼容成本低
- 短期最容易上线

**Cons**
- 仍然缺少 raw evidence 层
- recall 依旧建立在摘要之上，跨阶段追溯弱
- 无法支撑冻结交付场景下的强可解释召回

**Best when**
- 只想修一点 recall 体验，不想动 memory 基座

### 方案 B：evidence-first 的 workflow-native memory foundation

描述：
在现有 Beacon memory 面上新增原始证据层、artifact graph、stage context pack 和更强的 recall 排序，但保持 Beacon 仍是 workflow-native 工具，不扩张公开主命令面。

**Pros**
- 能补齐当前最大短板：原始证据、跨阶段寻址、强召回
- 与 Beacon 的需求冻结/交付证据主场景高度一致
- 可以分 P0/P1/P2 渐进落地

**Cons**
- 需要调整 memory 写回与 recall 结构
- 需要明确 truth / evidence / cache / projection 的边界

**Best when**
- 目标是给 Beacon 补“记忆基座”，而不是做通用脑系统

### 方案 C：直接引入 full brain platform

描述：
参考 `gBrain + MemPalace` 直接做通用知识操作系统，带完整 graph、timeline、background workers、数据库引擎。

**Pros**
- 能力上限高
- 可扩展空间大

**Cons**
- 明显超出 v1.3.6 的版本边界
- 会把 Beacon 从 workflow-native 拉向通用 knowledge OS
- infra、治理、产品语义都会失控

**Best when**
- 产品目标已经不再是 Beacon，而是独立 memory platform

---

## 3. Recommendation

推荐采用 **方案 B：evidence-first 的 workflow-native memory foundation**。

原因：

1. 它补的是 Beacon 当前真实缺口，而不是抽象幻想能力。
2. 它保留 Beacon 的主流程与版本纪律，不会把产品重心从“冻结与交付”拉偏。
3. 它能吸收 `MemPalace / gBrain / Evolver` 的强点，但避免照搬命名、存储和平台形态。

---

## 4. Key Decisions

- 决策 1：Beacon 的新记忆基座必须 `verbatim-first`，先存原始证据，再生成摘要与索引。
- 决策 2：Beacon 的 memory 仍然是 workflow-native，不做通用 CRM、个人脑、联系人脑。
- 决策 3：`memory-v1.json` 继续保留，但降级为 index / summary plane，不再承担全部真相。
- 决策 4：正式新增 `.beacon/memory/evidence/`，承载原始证据摘录、来源、阶段、artifact 关联。
- 决策 5：召回必须能解释“为什么命中”，默认返回 evidence refs、artifact refs、stage/run 上下文。
- 决策 6：`memory-friction-evolution` 不再只写一行 feedback，而要优先写 evidence-backed memory。
- 决策 7：默认不引入 Postgres / pgvector，优先保持本地 JSON + deterministic indexing；只有 JSON 明显失效时再考虑 SQLite。

---

## 5. Open Questions

- `artifact graph` 在 P1 是否直接用 JSON 邻接表，还是同步引入轻量 SQLite。
- `recall` 是否需要新增 `context` / `evidence` layer，还是复用现有 `index|timeline|detail` 并扩展语义。
- `implement / qa / release` 是否默认自动注入 stage context pack，还是先保留显式开关。
