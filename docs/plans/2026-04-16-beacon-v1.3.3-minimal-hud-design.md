# Beacon v1.3.3 极简心智 HUD 设计

**Date**: 2026-04-16  
**Version**: v1.3.3  
**Status**: Design Approved  
**参考**: jarrodwatts/claude-hud, anhannin/codex-hud, fwyc0573/codex-hud

## 1. 背景与目标

### 1.1 背景

Beacon v1.3.3 的核心目标是**极简瘦身**，将人类主面收敛为 `6+3` 命令：

- 6 个主命令：`prd → user-story → test-case → implement → qa → release`
- 3 个辅助：`help / status / doctor`

当前 Beacon 已有 HUD 基础设施（`team_hud.py`, `hud-state.json`），但缺乏统一的极简 HUD 设计。

### 1.2 目标

设计一个**极简但全面**的 HUD，满足以下需求：

1. **版本追踪** - 显示 Beacon 运行版本和文档版本
2. **工作流可视化** - 清晰展示当前在哪个阶段
3. **执行监控** - 详细监控 implement 三种模式的执行进度
4. **极简展示** - 默认 1-3 行，不干扰用户

### 1.3 参考方案分析

| 项目 | 核心特点 | 适用场景 | 借鉴点 |
|------|---------|---------|--------|
| **jarrodwatts/claude-hud** | 丰富可配置，多行详细显示 | Claude Code 执行细节观测 | 可视化进度条、符号语言 |
| **anhannin/codex-hud** | 极简单行：模型、git、使用窗口 | 核心状态一览 | 极简信息密度 |
| **fwyc0573/codex-hud** | Tmux 多会话、token 详细分解 | 多会话监控 | 执行模式分层展示 |

**Beacon HUD 的差异化**：
- ✅ 工作流感知（6 步主链可视化）
- ✅ 执行模式详细监控（single/team/ralph）
- ✅ 断路器状态实时显示
- ✅ 两阶段模型（需求 vs 执行）

## 2. 核心设计原则

### 2.1 两阶段工作流模型

将 Beacon 工作流简化为两个核心阶段：

1. **需求阶段** - prd + user-story + test-case（统一为一个状态）
2. **执行阶段** - implement 三种模式（详细监控）

**理由**：
- prd/user-story/test-case 都是需求准备，用户关心的是"需求是否完成"
- implement 是核心执行阶段，需要详细监控进度和状态
- qa/release 是后续阶段，暂时只需要显示"待执行"

### 2.2 信息分层原则

- **第一行**：上下文层（始终显示）- 版本、功能名、阶段
- **第二行**：执行层（仅执行阶段显示）- 模式、进度、耗时
- **第三行**：告警层（仅有问题时显示）- 断路器、错误信息

### 2.3 极简展示原则

- **符号优先** - 用 `✓ ◐ ✗ ⚠ ⛔` 代替文字
- **动态扩展** - 需求阶段 1 行，执行阶段 2-3 行
- **信息密度** - 每行不超过 80 字符
- **状态驱动** - 根据当前阶段自动调整显示内容

## 3. HUD 设计方案

### 3.1 需求阶段 HUD（1 行）

```
[beacon:v1.3.3] docs:v1.3.3 | feature-name | 需求✓ [执行] QA 发布
```

**信息组成**：
- `[beacon:v1.3.3]` - Beacon 运行版本
- `docs:v1.3.3` - 文档材料版本
- `feature-name` - 当前功能名（截断到 30 字符）
- `需求✓` - prd/user-story/test-case 都完成
- `[执行]` - 当前在执行阶段（用 `[]` 标记）
- `QA` / `发布` - 后续阶段

**状态变化**：
- 需求进行中：`[需求] 执行 QA 发布`
- 需求完成：`需求✓ [执行] QA 发布`
- 执行完成：`需求✓ 执行✓ [QA] 发布`

---

### 3.2 执行阶段 HUD - Single 模式（2 行）

```
[beacon:v1.3.3] docs:v1.3.3 | feature-name | 需求✓ [执行:single] QA 发布
▸ 执行中 | auth.py✓ config.py✓ test.py◐ | ⏱ 1m30s
```

**第二行信息**：
- `▸ 执行中` - 执行状态指示器
- `auth.py✓` - 已完成文件
- `config.py✓` - 已完成文件
- `test.py◐` - 正在处理文件
- `⏱ 1m30s` - 执行耗时

**适用场景**：
- 简单功能的单次执行
- 不需要并行或迭代的场景

---

### 3.3 执行阶段 HUD - Team 模式（3 行）

```
[beacon:v1.3.3] docs:v1.3.3 | feature-name | 需求✓ [执行:team] QA 发布
▸ 3 workers | w1:auth.py✓ w2:api.py◐ w3:test.py◐ | ⏱ 2m45s
  进度: 5/12 任务完成 (42%)
```

**第二行信息**：
- `3 workers` - 并行工作者数量
- `w1:auth.py✓` - worker1 完成 auth.py
- `w2:api.py◐` - worker2 正在处理 api.py
- `w3:test.py◐` - worker3 正在处理 test.py
- `⏱ 2m45s` - 执行耗时

**第三行信息**：
- `5/12 任务完成 (42%)` - 整体进度百分比

**适用场景**：
- 多文件并行处理
- 需要加速执行的场景

---

### 3.4 执行阶段 HUD - Ralph 模式（3 行）

```
[beacon:v1.3.3] docs:v1.3.3 | feature-name | 需求✓ [执行:ralph] QA 发布
▸ Round 3/∞ | circuit:ok | auth.py✓ api.py✓ test.py◐ | ⏱ 5m20s
  R1:实现✓ R2:修复✓ R3:优化◐ | 累计:3 文件修改
```

**第二行信息**：
- `Round 3/∞` - 第 3 轮迭代（无限循环）
- `circuit:ok` - 断路器状态（ok/warn/trip）
- `auth.py✓ api.py✓ test.py◐` - 本轮处理的文件
- `⏱ 5m20s` - 执行耗时

**第三行信息**：
- `R1:实现✓ R2:修复✓ R3:优化◐` - 各轮次状态和标签
- `累计:3 文件修改` - 累计修改统计

**适用场景**：
- 需要迭代优化的复杂功能
- 需要断路器保护的场景

---

### 3.5 告警状态（第 3 行，仅在有问题时显示）

#### 警告状态
```
⚠ circuit:warn | 重复错误:2次 | 建议:检查 auth.py
```

#### 熔断状态
```
⛔ circuit:trip | 熔断触发 | 原因:连续 3 次相同错误
```

**触发条件**：
- `circuit:warn` - 检测到 2 次相同错误
- `circuit:trip` - 检测到 3 次相同错误，停止执行

## 5. 状态符号表

| 符号 | 含义 | 使用场景 |
|------|------|---------|
| `✓` | 已完成 | 阶段/文件/轮次完成 |
| `[x]` | 进行中 | 当前阶段标记 |
| `◐` | 执行中 | 正在处理的文件 |
| `✗` | 失败 | 处理失败的文件 |
| `⏱` | 计时器 | 耗时显示 |
| `⚠` | 警告 | 断路器警告状态 |
| `⛔` | 阻塞 | 断路器熔断状态 |
| `▸` | 指示器 | 执行状态行前缀 |

---

## 6. 断路器状态详解

| 状态 | 显示 | 含义 | 触发条件 | 行为 |
|------|------|------|---------|------|
| 健康 | `circuit:ok` | 正常运行 | 无重复错误 | 继续执行 |
| 警告 | `circuit:warn` | 检测到重复 | 2 次相同错误 | 继续执行，显示警告 |
| 熔断 | `circuit:trip` | 停止执行 | 3 次相同错误 | 停止执行，等待人工介入 |

**断路器设计目标**：
- 防止 Ralph 模式陷入无限循环
- 及时发现重复性错误
- 保护系统资源

## 7. 数据结构设计

### 7.1 HUD 状态数据结构

```python
{
  "beacon_version": "v1.3.3",
  "docs_version": "v1.3.3",
  "feature": "auth-refactor",
  "stage": "implement",  # 需求 | 执行 | QA | 发布
  "requirement_complete": true,
  
  "execution": {
    "mode": "ralph",  # single | team | ralph
    "status": "in_progress",
    
    # Single 模式
    "current_file": "test.py",
    "completed_files": ["auth.py", "config.py"],
    
    # Team 模式
    "workers": [
      {"id": "w1", "file": "auth.py", "status": "completed"},
      {"id": "w2", "file": "api.py", "status": "in_progress"},
      {"id": "w3", "file": "test.py", "status": "in_progress"}
    ],
    "progress": {"completed": 5, "total": 12},
    
    # Ralph 模式
    "round": 3,
    "rounds_history": [
      {"round": 1, "label": "实现", "status": "completed"},
      {"round": 2, "label": "修复", "status": "completed"},
      {"round": 3, "label": "优化", "status": "in_progress"}
    ],
    "files_modified_total": 3,
    
    # 断路器
    "circuit": {
      "status": "ok",  # ok | warn | trip
      "repeat_errors": 0,
      "last_error": null
    },
    
    "elapsed": "5m20s"
  }
}
```

### 7.2 存储路径

```
.beacon/state/hud/<run_id>.json          # 单次执行的 HUD 状态
.omc/state/sessions/<session_id>/hud-state.json  # 会话级 HUD 状态
```

## 8. 技术实现建议

### 8.1 渲染逻辑

```python
def render_hud(state: dict) -> list[str]:
    """渲染 HUD，返回 1-3 行文本"""
    lines = []
    
    # 第一行：始终显示
    lines.append(render_context_line(state))
    
    # 第二行：执行阶段才显示
    if state["stage"] == "执行" and state["execution"]["mode"]:
        lines.append(render_execution_line(state))
    
    # 第三行：有告警或进度详情才显示
    if state["execution"].get("circuit", {}).get("status") != "ok":
        lines.append(render_alert_line(state))
    elif state["execution"]["mode"] in ["team", "ralph"]:
        lines.append(render_progress_line(state))
    
    return lines
```

### 8.2 更新频率

- **需求阶段** - 阶段切换时更新（低频）
- **执行阶段** - 每 1-2 秒更新一次（中频）
- **断路器状态** - 实时更新（高频）

### 8.3 颜色方案（可选）

| 元素 | 颜色 | 说明 |
|------|------|------|
| 版本信息 | cyan | 静态信息 |
| 功能名 | yellow | 当前上下文 |
| 完成标记 `✓` | green | 成功状态 |
| 进行中 `◐` | blue | 执行中 |
| 失败 `✗` | red | 错误状态 |
| 警告 `⚠` | yellow | 警告级别 |
| 熔断 `⛔` | red | 严重问题 |

## 10. 验收标准

### AC-001：版本信息显示
- HUD 第一行必须显示 `[beacon:v1.3.3] docs:v1.3.3`
- 版本信息必须从配置文件动态读取

### AC-002：两阶段工作流
- 需求阶段显示：`需求✓ [执行] QA 发布`
- 执行阶段显示：`需求✓ [执行:mode] QA 发布`

### AC-003：Single 模式监控
- 显示当前处理文件和已完成文件
- 显示执行耗时

### AC-004：Team 模式监控
- 显示 worker 数量和各 worker 状态
- 显示整体进度百分比

### AC-005：Ralph 模式监控
- 显示当前轮次和轮次历史
- 显示断路器状态
- 显示累计修改统计

### AC-006：断路器告警
- `circuit:warn` 时显示警告行
- `circuit:trip` 时显示熔断行
- 告警信息包含错误次数和建议

### AC-007：极简展示
- 需求阶段只占 1 行
- 执行阶段占 2-3 行
- 每行不超过 80 字符

### AC-008：状态更新
- 执行阶段每 1-2 秒更新一次
- 断路器状态实时更新

## 12. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| HUD 更新频率过高导致性能问题 | 中 | 限制更新频率为 1-2 秒，使用增量更新 |
| 断路器误判导致正常执行被中断 | 高 | 提供手动重置断路器的机制 |
| 多行显示在小终端窗口中显示不全 | 低 | 提供单行压缩模式 |
| 与现有 team_hud 实现冲突 | 中 | 复用现有路径结构，扩展而非替换 |
