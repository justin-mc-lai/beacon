# Beacon v1.3.9 Agents Brainstorm

## What We're Building

Beacon `v1.3.9` 需要补强 agents 能力，但不能把 Beacon 变成一个“公开暴露一堆 agent/runtime 细节”的产品。方向应保持：

- 人类主面仍然只有 `prd -> user-story -> test-case -> prototype -> implement -> qa -> release`
- agents 作为内部执行面增强可靠性、可追踪性、可恢复性
- 对外只暴露更稳定的结果、证据和 next step

本次参考样本来自：

- 克隆路径：
  `/Users/apple/Developer/Personal/oss-sync/agents/openai-agents-python`
- 源仓库：
  `https://github.com/openai/openai-agents-python`

这个仓库对 Beacon 最有价值的不是“照搬 SDK API”，而是它对以下主题的拆分很清楚：

- agent
- runner
- handoff
- guardrail
- tracing
- session
- sandbox / workspace agent

Beacon 当前已把 agents 用在 `implement` 下，`v1.3.9` 应该补的是：

1. 哪些生命周期阶段也适合 agent 模式
2. agent 模式如何保持 requirement truth 不漂
3. agent mode 如何变得更可靠，而不是更复杂

## Why This Approach

我不建议把 `openai-agents-python` 当成“多 agent 框架替换方案”，而建议把它当成 Beacon 的设计参考系。

### Approach A: 直接模仿 SDK 公开大量 agent 原语

**Pros:**
- 能快速获得一套看起来完整的 agent 词汇表
- 实现时可以直接映射 `handoff / guardrail / session / tracing`

**Cons:**
- 会破坏 Beacon 既有的人类极简命令面
- 容易把内部运行细节暴露成新的对外 surface

**Best when:** 你想做通用 agents SDK，而不是 Beacon 这种 lifecycle kernel。

### Approach B: 保持 Beacon 主面不变，只吸收 agent 运行原则

**Pros:**
- 与 Beacon 全局边界一致
- 可以增强 `implement / qa / release-support` 的内部可靠性
- 更容易把 agents 能力落到 deterministic evidence 与 writeback 上

**Cons:**
- 需要自己做一层 Beacon 风格投影，而不是直接套 SDK 结构
- 短期内不会显得“功能暴增”

**Best when:** 你要的是“更稳的 Beacon”，不是“更多新的 agent 命令”。

我推荐 **Approach B**。

## Key Decisions

- 决定 1：Beacon 不新增新的公开一级 agent 命令。
  原因：这会直接违反当前 global boundaries 的最小人类面约束。

- 决定 2：把 `openai-agents-python` 的价值抽象成 6 个内部能力面。
  原因：Beacon 真正缺的是 agent execution discipline，不是 agent 名词表。

- 决定 3：`implement` 继续是 agent 最重的使用面，但不是唯一使用面。
  原因：`qa / release-support / doctor / archive validation` 同样存在明确的 agent 子任务边界。

- 决定 4：Beacon agents 必须绑定 requirement truth、transaction lineage、traceability refs。
  原因：如果 agent 只是“多开几个执行器”，但不绑定 truth 和证据，它只会增加噪音。

- 决定 5：Beacon 需要区分三类 agent orchestration。
  原因：不是所有阶段都适合同一种 manager/handoff 模式。

## OpenAI Agents SDK 对 Beacon 的 6 个参考点

### 1. Runner / run loop

`openai-agents-python` 的强点是把：

- LLM turns
- tool calls
- handoffs
- final output

放进统一 runner loop。

Beacon 可借鉴：

- 每个 lifecycle stage 都需要明确的 runner contract
- runner 必须定义“何时继续、何时停、何时转交、何时要求人类介入”

### 2. Handoffs

SDK 里 handoff 是显式一级概念。

Beacon 可借鉴：

- `implement -> qa`
- `qa -> repair`
- `release -> doctor/repair`

这些都应有正式 handoff envelope，而不是只靠散落 markdown 和经验判断。

### 3. Guardrails

SDK 把 input/output/tool guardrails 区分得很清楚。

Beacon 可借鉴：

- requirement-bound guardrail
- stage-bound guardrail
- tool/evidence guardrail

尤其适合：

- `qa` 前检查 evidence readiness
- `release` 前检查 acceptance / change docs / gate convergence
- `doctor` 前检查上下文版本漂移

### 4. Tracing

SDK 默认 trace agent runs、tool calls、handoffs、guardrails。

Beacon 可借鉴：

- 每个 agent round 必须留下 structured trace
- trace 应接到 `docs/beacon/<version>/execution/` 的 human-readable projection
- `help/status/doctor` 只读取 trace summary，不暴露底层噪音

### 5. Sessions / resumability

SDK 把 session 作为一等能力。

Beacon 可借鉴：

- `qa` 需要 stronger resumability
- `ralph` 需要更稳定的 round resume
- `doctor` 需要从 session / state 中判断是否安全恢复

### 6. Sandbox / workspace agent

SDK 的 sandbox agent 强调：

- workspace-scoped execution
- longer-running state
- file/patch/tool actions

Beacon 可借鉴：

- implement team agents
- qa repair loops
- real-project validation isolated worktree

这对 Beacon 尤其重要，因为 Beacon 本来就需要 version branch / isolated worktree / deterministic artifacts。

## Beacon Lifecycle 哪些场景适合 agents

### 已知适合：implement

这是当前已经成立的场景。

适合模式：

- manager + specialist roles
- plan -> architect -> implement -> review -> test
- Ralph controller 做 post-freeze routing

### 适合补强：qa

这是 `v1.3.9` 最应该扩的下一站。

适合模式：

- manager agent 做 coverage / evidence routing
- specialist agents 分别处理：
  - contract
  - integration
  - regression
  - acceptance writeback

重点不是“多 agent 测试”，而是：

- 多层 evidence 收敛
- acceptance dual-write
- repair handoff 更结构化

### 适合补强：release support

不建议把 `release` 本身变成复杂 agent stage，但适合内部 agent sidecar：

- release artifact completeness auditor
- change-doc coverage checker
- gate/release convergence verifier

### 适合补强：doctor

`doctor` 天然适合 agent 化，因为它本来就是 diagnosis / repair suggestion surface。

可用场景：

- context drift diagnosis
- version mismatch diagnosis
- materials sync blocker explanation
- runtime ledger repair reasoning

### 适合补强：archive / historical truth validation

archive 不需要“执行型多 agent”，但适合：

- archive classification agent
- archive consumption safety checker
- historical truth isolation explainer

### 谨慎使用：prd / user-story / test-case

这些阶段可以用 agent 辅助，但不应让 agent 取代 frozen truth authoring contract。

适合：

- requirement gap detection
- ambiguity detection
- coverage suggestion

不适合：

- 自动自由改写 frozen truth

### 不建议扩张：prototype 公开 agent 化

prototype 内部可以继续用 semantic/compiler/trace 机制，但不建议再对外暴露一层 “prototype agents”。

原因：

- 这会让主面变复杂
- prototype 已经有自己的 projection discipline

## Beacon v1.3.9 应新增的 Agents 能力面

### A. Agent Run Contract

给 Beacon agent runs 增加统一 contract：

- run_id
- stage
- feature
- version
- requirement_binding
- evidence_refs
- stop_state
- next_action
- handoff_ref

### B. Handoff Envelope

把以下 handoff 正式化：

- implement -> qa
- qa -> implement-repair
- qa -> release
- release -> doctor

### C. Agent Guardrail Layers

建议固定三层：

- truth guardrail
- execution guardrail
- evidence guardrail

### D. Agent Trace Projection

为 agent traces 增加 human projection：

- 不是把 raw trace 全暴露
- 而是输出 execution-facing concise summaries

### E. Session / Resume Contract

把 `qa`、`ralph`、`doctor` 的 resume 条件显式化：

- safe_to_resume
- stale_context
- replay_required
- human_confirmation_required

### F. Agent Reliability Score

Beacon 需要自己的 agent reliability read model，例如：

- handoff success rate
- replay rate
- repair loop depth
- false complete risk
- operator interruption rate

## Open Questions

- `qa acceptance dual-write` 是否还应拆出独立 “acceptance-writer” agent，还是继续保留在当前 `qa run` 主流程里更简单
- `release` 是否只需要 agent auditor sidecar，而不需要正式 `team`/`ralph` runtime
- `doctor` 的 agent trace 是否要进入 public human docs，还是只保留 summary projection
