# Beacon 当前能力特性清单 v1

**日期**: 2026-05-03  
**定位**: 只读能力盘点 / 版本演进分析  
**范围**: 基于当前仓内 `v1.3.9`、`v1.3.10`、`v1.3.11` 正式材料与现有命令面，对 Beacon 当前能力做三层拆分：`已实现 / 半实现 / 规划中`。  

---

## 1. 一句话判断

Beacon 当前已经不是单纯的文档生成器，也不是纯 agent runtime。

它更准确的定位是：

> 一个 **evidence-first、requirement-first** 的产品交付内核，用版本化 requirement truth、machine projection、QA、gate 与 release 把需求到交付的闭环收口到同一条可审计链路里。

当前最强能力在于：

- 版本化 requirement truth 治理
- machine mirror / anti-drift
- QA / release / evidence 闭环
- project metadata / branch contract 治理

当前仍然偏弱的部分在于：

- 真正统一的 orchestration runtime
- 长任务 scheduler / workspace isolation
- Symphony 水位的 operator control plane

---

## 2. 已实现

### 2.1 版本化 requirement 主链

Beacon 已经正式建立主生命周期：

```text
prd -> user-story -> test-case -> prototype -> implement -> qa -> release
```

并将正式材料统一落在：

- `docs/beacon/<version>/`

这意味着 Beacon 已经具备：

- 按版本冻结 requirement materials
- 按版本推进实现与 QA
- 按版本做 release 对齐与回看

### 2.2 Requirement truth 治理

Beacon 已经形成了稳定的 requirement truth 约束：

- PRD、user-story、test-case、prototype 都有正式文档面
- 同时存在 human / machine 双面材料
- 支持 `freeze / reopen / change loop / revision binding`
- requirement truth 被明确设定为唯一 scope 来源

当前执行层不得反向改写：

- `prd`
- `user-story`
- `test-case`
- `prototype`

### 2.3 PRD anti-drift 与 machine reconcile

Beacon 已经具备比较强的 PRD machine mirror 治理能力：

- `prd reconcile`
- PRD audit
- `doctor verify-materials --strict`
- latest pointer / supersedes transaction 语义

当前它已经能发现：

- human markdown 改了但 machine mirror 没更新
- requirement package 有单面漂移
- release 所依赖的 materials 存在 stale projection

### 2.4 Gate / release / evidence 闭环

Beacon 当前 release 面已经比较完整，核心能力包括：

- `doctor`
- `gate`
- `release check`
- `release scorecard`
- evidence manifest
- acceptance envelope
- coverage summary
- QA scorecard

当前 release / gate 已经不是“读几个测试结果”，而是在核验：

- artifact version
- run_id 一致性
- evidence hash
- acceptance transaction
- revision binding
- semantic contract
- prompt boundary

### 2.5 项目元信息治理

Beacon 已经形成项目与版本执行面的正式 metadata contract：

- project topology
- service binding
- version-scoped branch contract
- default execution service
- participating services

对应命令面已经收口到：

- `beacon doctor metadata verify`
- `beacon doctor metadata update`

并且这些 metadata 已经进入 QA / release 门禁，而不是停留在辅助说明层。

### 2.6 Prototype requirement closure

Beacon 当前的 `prototype` 已经不是简单线框稿。

它已经具备以下 requirement closure 能力：

- `DESIGN.md`
- preview HTML
- design context
- design reasoning / design artifacts
- UX truth 投影

方向上已经明确：

- prototype 仍属于 requirement-driven freeze
- 但它同时承担 UI/UX 类 PRD 编译的一部分职责

### 2.7 Support surface 与治理辅助面

Beacon 当前已经形成一组比较完整的 support surfaces：

- `help`
- `status`
- `archive`
- `friction-intake`
- `report`
- `review`
- `real-project-validation`

这些能力已经能承担：

- requirement remediation 指引
- delivery closure 导航
- friction 采集与治理
- 真实项目 release proof

### 2.8 Host runtime / skill 兼容性基础

Beacon 已经做过一轮 host runtime 兼容性与 skill admission 收口：

- Codex / Claude runtime compatibility
- host-validated third-party skill compatibility
- skill admission / validation contract

这意味着 Beacon 已经不再是假设“只有一个固定宿主、只有一种执行环境”的工具。

## 3. 半实现

### 3.1 Runtime projection / delivery read model

当前 `status` 已经能聚合多类运行态信息：

- runtime projection
- release scorecard
- control plane
- portfolio / project detail
- workflow progress
- requirement package gate

但它目前更像：

- 多来源运行摘要

而不是：

- 单一 authoritative runtime state

### 3.2 Board / operator workbench

当前 Beacon 已经有：

- `beacon board`
- prototype-backed local board launcher
- board action dispatch

但它目前更接近：

- 从 frozen prototype bundle 启动的本地 board surface

而不是：

- 真正成熟的 operator workbench / live control console

### 3.3 Execution runtime kernel

`v1.3.11` 已经正式把 runtime kernel 写进 requirement truth：

- `WorkItem`
- `Run`
- `Workspace`
- `RetryEntry`
- `ExecutionHost`
- `OperatorAction`

也已经明确要求：

- admission
- ordering
- retry
- reconcile
- workspace isolation
- recovery contract

但当前状态更像：

- runtime kernel 的 requirement truth 已建立
- 局部 gate / release / board contract 已开始消费
- 真正统一宿主还没有完全落地

### 3.4 Cross-surface runtime contract

当前 `implement / qa / release / status / board` 已经开始共享：

- 一部分 reason code
- 一部分 delivery read model
- 一部分 release-binding / acceptance contract

但仍存在明显问题：

- 很多 surface 还在自己拼状态
- 还没有完全单源化的 runtime host

### 3.5 Prototype -> implement / qa shared contract

方向已经成立：

- prototype 产出的 UX truth 应被 implement / qa 共同消费

但当前还没有完全稳定到：

- 一份统一 UX contract 持续驱动实现、校验与 release

目前仍处于：

- requirement truth 已补齐
- 局部实现已打通
- 还未形成完全稳定、跨 surface 的强约束

### 3.6 SQLite / runtime ledger 使用

Beacon 当前已经有一些 runtime ledger 基础：

- metadata projection
- friction queue
- runtime projection store

但它还不是 Symphony 那种：

- 常驻 orchestrator ledger
- scheduler-first control plane

换句话说，Beacon 已经在“有投影账本”，但还没有进入“靠统一运行账本驱动长任务编排”。

---

## 4. 规划中

### 4.1 真正的 orchestration runtime

后续最核心的缺口，不是再补更多文档，而是把 runtime host 真正实现出来，包括：

- 单一 authoritative runtime state
- work item admission
- run scheduler
- bounded concurrency
- retry / reconcile / recovery lifecycle
- feature ordering / waves

### 4.2 Workspace isolation 内核

Beacon 后续要进一步具备：

- per-run workspace
- writable scope contract
- baseline binding
- drift detection
- interrupted run recovery

这是它从“交付治理工具”迈向“长任务运行系统”的关键台阶之一。

### 4.3 统一 agent runner / worker runtime

当前 `implement` 仍更像 surface-specific execution + skill adapter。

后续需要收口为：

- 统一 coding agent runner contract
- surface 通过 runtime host 调度 runner
- implement / qa / validation 共用一套 worker runtime 能力

### 4.4 成熟的 operator workbench

真正成熟的 workbench 还需要：

- execution board
- run detail
- retry / stop / continue / repair actions
- recovery diagnostics
- baseline host health
- feature wave ordering
- operator alert surface

也就是说，当前 board 只是入口，真正的 operator console 仍在后续版本。

### 4.5 Tracker-driven orchestration

Beacon 目前 work item 的正式来源仍然主要是 frozen requirement package。

后续若向 Symphony 靠拢，需要新增：

- issue / work item source adapter
- tracker polling / ingestion
- eligibility rules
- tracker state 与 runtime state 的协同

但这属于 requirement truth 之外的新执行层，不能倒过来喧宾夺主。

### 4.6 Symphony 水位的长任务控制平面

如果把目标定到 `openai/symphony` 那个水位，Beacon 后面还需要补：

- 常驻 scheduler
- polling / dispatch loop
- 多 run 并发管理
- workspace lifecycle manager
- restart 后 reconciliation
- runtime-first observability dashboard

当前 Beacon 还没有完整到这一层。

---

## 5. 当前阶段的总判断

### 5.1 Beacon 现在最强的是什么

Beacon 现在最强的是：

- requirement truth 治理
- machine mirror anti-drift
- QA / evidence / release gate 闭环
- project metadata / branch governance

它已经是一套比较完整的：

> versioned requirement + delivery governance kernel

### 5.2 Beacon 现在还不是什么

Beacon 现在还不是：

- 完整长任务调度系统
- Symphony 式 scheduler / runner / control plane
- 真正成熟的 operator runtime console

### 5.3 当前最合理的演进方向

后续最合理的重点不是继续扩张文档面，而是：

1. 把 `v1.3.11` 已经定义出来的 runtime kernel 真正实现
2. 统一 workspace / run / retry / recovery contract
3. 让 board 建立在 authoritative runtime state 之上
4. 最后再考虑 tracker-driven orchestration 与 Symphony 水位的控制平面

---

## 6. 结论

Beacon 当前的真实状态可以压缩成一句话：

> 它已经非常接近一套完整的 requirement-first 交付治理内核，但还没有完全跨过那一步，成为真正的长任务 orchestration runtime。

因此：

- **已实现**：需求真相、机器投影、QA、release、metadata 治理
- **半实现**：runtime projection、board、runtime kernel contract、cross-surface runtime read model
- **规划中**：scheduler、workspace isolation、统一 runner、成熟 operator workbench、tracker-driven orchestration
