# Beacon v1.4.0 Feasibility: Lightweight Refactor While Strengthening Change and Implement

## 1. 目标

本稿基于以下输入，判断 `v1.4.0` PRD 提出的方向是否同时满足三件事：

1. 在减负的同时增强 `change`
2. 在减负的同时增强 `implement`
3. 整体方案在实现上可行、可验证、可审计

输入依据：

- `docs/beacon/v1.4.0/prd/beacon-v1.4.0-lightweight-kernel-and-core-surface-refactor.md`
- `beacon/utils/material_sync.py`
- `beacon/utils/ralph_runtime.py`
- `beacon/commands/implement.py`
- `beacon/commands/gate.py`
- `skills/beacon/beacon-change/SKILL.md`
- `oss-sync/automation/autoresearch/openspec/docs/workflows.md`
- `oss-sync/automation/autoresearch/openspec/src/commands/change.ts`
- `oss-sync/agents/tools/codex/codex-rs/features/src/lib.rs`
- `oss-sync/agents/tools/codex/codex-rs/tools/src/goal_tool.rs`

## 2. 高置信度结论

高置信度结论如下：

- `v1.4.0` 的总体方向是可行的
- “减负 + 增强 change” 是可行的，但前提是 `change` 必须从零散路由提升为单一事务单元
- “减负 + 增强 implement” 也是可行的，但前提是 Codex goal 只能作为 execution-side optional capability，而不能变成新的 truth source
- 这两块都可以做到可验证、可审计
- 真正的风险不在“做不到”，而在“做成新的重投影层”

换句话说：

> 方案不是不可实现，而是必须严格按“truth 不变、contract 收敛、execution 能力可选注入、projection 不升格为真相”的方式实现。

## 3. 第一性原理判断

### 3.1 为什么“减负同时增强”在这里成立

表面看，减负与增强是冲突的。  
但对 Beacon 来说，这两者并不矛盾，因为当前系统的重量主要来自：

- truth 外的重复 artifact
- gate / implement / qa 对碎片 machine 面的耦合
- 变更与实现状态分散在太多读写面

所以只要做的是：

- 收敛 contract
- 收敛 change identity
- 收敛 implement execution state

就会同时得到两种收益：

1. 系统更轻
2. 核心链路更强

### 3.2 什么情况下会失败

如果 `v1.4.0` 最终做成下面这种形态，就会失败：

- 保留现有碎片 machine 面不动，再额外增加 compiled contract
- 保留现有 change-impact / release change docs / reopen sync 分散逻辑不动，再额外加 change kernel
- 保留 Ralph state 不动，再额外堆一层 goal state mirror

那结果不是减负，而是：

> 旧重量不减，新能力又叠上去。

## 4. 对 `change` 的可行性判断

### 4.1 当前源码状态

从现有实现看，Beacon 已经有 change 相关信号，但还没有成型 change kernel：

- `beacon-change` 是 router，不是一等命令内核
- `sync_change_loop_requirement_package()` 已经存在 change-loop refresh 逻辑
- gate / help / status / qa / prototype 都会推荐 `beacon-change`
- release 会生成 per-feature 和 per-version change 文档
- `change-impact.json` 已是现有 gate 输入之一

这说明：

- Beacon 并不是“没有 change”
- Beacon 是“已经知道 change 必须存在，但还没把它收敛成单一事务单元”

### 4.2 为什么增强 `change` 是可行的

增强 `change` 可行，原因有三：

1. 现有系统已经存在 change 触发点
2. 现有系统已经存在变更后的 requirement resync 路径
3. 现有系统已经存在 release 级变更聚合语义

所以 `v1.4.0` 并不是从 0 开始发明 change，而是把这些已有碎片收敛为：

- 单一 `change_id`
- 单一 `change contract`
- 单一 `change archive / verify / refreeze` 路径

### 4.3 对 OpenSpec 的借鉴是否合理

合理，但只能借鉴它的“变更工作单元”，不能照搬它的公开工作流。

OpenSpec 真正值得借鉴的是：

- 一个 change 有稳定身份
- 一个 change 的 proposal/specs/design/tasks 围绕同一目录
- validate 与 archive 围绕同一 change
- 并行 change 有明确边界

Beacon 可以借鉴为：

- frozen truth 变更必须有正式 change identity
- refreeze / implement delta / qa delta / release recheck 共用同一 change identity
- status/help/report/gate 能统一指向同一 change contract

Beacon 不该照搬为：

- 再造一套新的公开 lifecycle
- 用 change 替换 `prd -> user-story -> test-case -> implement -> qa -> release`

### 4.4 `change` 的可验证性

增强后的 `change` 是可验证的，前提是它至少满足：

- 每次变更都有 `change_id`
- 每次变更都能指向：
  - `target_version`
  - `target_feature`
  - `baseline_revision`
  - `affected_truth_refs`
  - `affected_layers`
  - `verification_refs`
- gate 可以检查：
  - change contract 是否存在
  - baseline 是否匹配
  - refreeze 是否完成
  - delta QA 是否完成
  - release recheck 是否引用同一 change

也就是说，change 的验证不是“看有没有写文档”，而是：

> 检查同一 change identity 是否贯穿 requirement 变更、实现、验收、发布重检。

### 4.5 `change` 的可审计性

增强后的 `change` 也是可审计的，前提是把审计焦点放在 contract，而不是聊天历史：

- 谁触发了 change
- 为什么触发
- 改了哪份 truth
- 影响哪几层
- 哪次 refreeze 生效
- 哪轮 implement / qa / release consume 了这次 change

只要这些都落到：

- truth doc
- compiled change contract
- runtime change state

就具备正式审计能力。

## 5. 对 `implement` 的可行性判断

### 5.1 当前源码状态

现有 Beacon 的 `implement` 已经具备较强基础：

- requirement package 输入
- host runtime detection
- runtime/delegation precheck
- implementation plan
- git workflow contract
- Ralph runtime state
- writeback / QA handoff

`ralph_runtime.py` 也已经具备：

- round state
- stop_state
- current_blocker
- next_action
- recommended_command
- release-ready / human-blocked / budget-exhausted 等收尾语义

这说明 Beacon 距离“更强 implement 闭环”并不远。

### 5.2 Codex goal 接入是否可行

可行，但必须明确它是 host capability，不是 truth capability。

当前 Codex goal 具备以下事实：

- 是 experimental feature
- 是 persisted thread goal
- 有 `active / paused / budgetLimited / complete`
- 有 token/time accounting
- 有 model-visible tools，但模型只能安全地做有限状态更新

所以 Beacon 接入 Codex goal 的正确方式是：

- 当 host=codex 且 goals enabled 时，`implement` 可选创建或接入 goal
- goal 只负责 execution continuity、budgeting、handoff
- goal 不定义 requirement completeness
- goal 不定义 gate pass/fail
- goal 不定义 release readiness

### 5.3 为什么 goal 接入不会违背“减负”

因为它不是新增 truth 面，而是替换一部分当前隐式的执行上下文丢失问题。

如果不接 goal，长任务执行态通常散落在：

- thread 当前上下文
- Ralph state
- implementation summary
- host prompt trace
- 人类记忆

这其实已经是隐性重量。

如果用 goal 收敛成明确 execution state：

- `goal_objective`
- `goal_status`
- `tokens_used`
- `time_used_seconds`
- `goal_thread_id`

反而会减少“执行上下文漂移”。

### 5.4 Ralph 与 goal 的闭环是否可行

可行，而且应该做。

原因是 Ralph 当前已经有“自动执行多轮后停在正确位置”的雏形，只是还缺：

- 跟 thread-level persistent objective 的绑定
- 跟 budget-limited 的正式联动
- 跟 QA handoff 的统一状态映射

把 Ralph 与 goal 联起来后，最自然的链路是：

`truth -> implementation plan -> goal objective -> Ralph rounds -> verification -> QA handoff`

这条链是可行的，因为：

- goal 提供持续目标与预算视角
- Ralph 提供多轮执行与停止点
- Beacon gate/qa 继续提供 completion truth

### 5.5 `implement` 的可验证性

增强后的 implement 是可验证的，只要建立以下映射：

- requirement package -> goal objective
- goal status -> implement state
- Ralph round -> execution evidence
- QA handoff -> verification boundary

至少应验证：

- 当 host 支持 goal 时，goal 是否被创建或接入
- goal objective 是否来自 implementation plan / requirement package，而不是自由文本漂移
- `budget_limited` 时是否正确进入收尾或 handoff
- `complete` 时是否进入 verification / QA handoff，而不是直接宣称 release ready

### 5.6 `implement` 的可审计性

增强后的 implement 也是可审计的，只要明确：

- goal 是 execution telemetry，不是 truth
- Ralph rounds 是 execution evidence，不是 acceptance evidence
- QA/gate verdict 仍来自 Beacon 自身 acceptance chain

因此审计需要分三层：

1. truth audit
2. execution audit
3. acceptance audit

其中：

- goal + Ralph 属于 execution audit
- gate + QA evidence 属于 acceptance audit

只要这层次不混，审计就是成立的。

## 6. 最大实现风险

### 6.1 风险一：把 change 做成第二套 truth

如果 change contract 变成独立真相源，而不是 frozen truth 的受控变更单元，就会失败。

约束必须是：

- change 只能描述 truth 变化
- 真正 freeze 后的权威内容仍回到 `docs/beacon/<version>/...`

### 6.2 风险二：把 goal 做成完成定义

如果未来实现里出现：

- goal complete = implement complete
- goal budget limited = feature blocked

这种逻辑，就是错误的。

goal 只能定义：

- execution continuity
- budget / pause / resume
- thread-level stop summary

不能定义：

- requirement closure
- QA pass
- release pass

### 6.3 风险三：减负没有减掉旧输入面

如果 `compiled contract`、`change contract`、`goal mapping` 都加了，但 `gate` 仍继续读一堆 legacy mirror，减负就会失效。

所以必须坚持：

- 先双读
- 再单读
- 再降级 projection

## 7. 最小可行落地路径

### 7.1 Change Kernel MVP

第一阶段只做：

- `change_id`
- `change contract`
- gate 检查 change contract 存在性与 refreeze 完成性
- release 从 per-change contract 聚合 version summary

先不要一开始就扩大量 change 模板。

### 7.2 Goal Integration MVP

第一阶段只做：

- host=codex 且 goals enabled 时创建/接入 goal
- 记录 `goal_thread_id / goal_status / tokens_used / time_used_seconds`
- `budget_limited` -> Ralph 收尾或 handoff
- `complete` -> verification / QA handoff

先不要一开始就做复杂的跨 host 抽象统一层。

### 7.3 Audit MVP

第一阶段至少确保三件事：

1. change contract 可追踪
2. goal / Ralph execution state 可追踪
3. acceptance verdict 不被 execution state 越权覆盖

## 8. 结论

### 8.1 总体 verdict

`v1.4.0` PRD 提出的方向：

- 在减负同时增强 `change`
- 在减负同时增强 `implement`

是可行的。

### 8.2 条件 verdict

但它只在以下条件下成立：

- `change` 被做成一等事务单元，而不是继续散落在路由与报表里
- Codex goal 被视为 execution capability，而不是 truth capability
- Ralph 与 goal 的联动只增强执行闭环，不替代 QA/gate
- minimal machine contract 真正取代旧主路径输入，而不是叠加其上

### 8.3 可验证 / 可审计 verdict

本方案也是可验证、可审计的，前提是把以下三层严格分开：

1. truth layer
2. execution layer
3. acceptance layer

只要这三层不混，Beacon 就能同时做到：

- 更轻
- 更强
- 更可追踪

## 10. 最终建议

最合理的下一步不是继续扩 PRD，而是拆三组 user stories：

1. change kernel stories
2. goal-driven implement stories
3. audit / verification boundary stories

这样可以保持 `v1.4.0` 的减负主线，同时避免在实现层重新长出一层新重量。
