# Beacon v1.4.0 Human-Surface Skill Audit: iteration-governance and prototype-reconcile

## 1. 目标

本稿针对两类当前会影响 Beacon 人类心智面的 skill 做只读审计：

- `skills/beacon-iteration-governance/`
- `skills/beacon-prototype-reconcile/`

重点回答：

1. 它们的来源是什么
2. 它们的真实用途是什么
3. 它们是否必要
4. 它们是否应该继续出现在 Beacon 人类面可见技能集合里
5. 对 `v1.4.0` 轻量内核与极简人类面目标的影响是什么

## 3. 高置信度结论

高置信度结论如下：

- 这两个 skill 都不是 Beacon 主生命周期的一部分
- 它们都不是通用终端用户的人类面主入口
- 它们有用途，但用途高度特化
- 把它们暴露在 Beacon 默认人类面里，会污染用户心智

更具体地说：

- `beacon-iteration-governance`
  - 是 **Beacon 仓库自开发/自发布治理 skill**
  - 不是 Beacon 作为产品对外的用户工作流 skill
- `beacon-prototype-reconcile`
  - 是 **项目级、takeover/对账场景的外挂式 prototype reconcile skill**
  - 不是 Beacon 的标准 prototype 生命周期 skill

所以它们的问题不是“没有价值”，而是：

> 它们处于错误的人类面暴露层级。

## 4. `beacon-iteration-governance` 分析

## 4.1 来源

从 git history 和 skill 内容可以确认，这个 skill 最早是 Beacon 自仓库演进时引入的 repository-local governance tool。

它的目标并不是服务“使用 Beacon 的项目”，而是服务：

- Beacon 源码自身迭代
- 当前 release line 文档对齐
- Beacon 自己的 release verification

也就是说，它是：

> Beacon 开发者工具，不是 Beacon 最终用户流程工具。

## 4.2 用途

它做的事很明确：

- source changes
- README / current docs / skill surfaces convergence
- material / delivery / release checks

适用场景是：

- Beacon 仓库维护
- Beacon runtime 升级
- Beacon 文档收敛
- Beacon 自发布校验

它甚至显式要求：

- 对齐 `README.md`
- 对齐 `skills/beacon/`
- 对齐 `docs/beacon/<current>/`

这说明它是：

- repo-maintainer workflow
- self-hosted governance loop

而不是普通使用者的 project skill。

## 4.3 是否必要

必要，但必要性属于：

- **内部维护必要**

而不是：

- **外部用户默认必要**

它对 Beacon 自身持续演进是合理的，因为 Beacon 本身确实需要：

- current docs convergence
- delivery / release verification
- self-governance loop

但这不等于它应进入用户的默认人类面词表。

## 4.4 对用户心智的影响

如果用户在 Beacon skill 列表里看到它，会自然推测：

- Beacon 官方建议存在一个叫 iteration governance 的常规人类面
- 可能 Beacon lifecycle 里还有一个“迭代治理阶段”
- 用户可能需要理解 docs convergence / release verification 这些 Beacon 自开发内部概念

这与 `global-boundaries.md` 的核心原则冲突：

- 人类主流程极简
- support 面克制
- 复杂度默认留在机器内部

所以它对用户心智的影响是：

- **高污染**
- **低通用性**
- **误导性强**

## 4.5 最终判断

`beacon-iteration-governance`：

- **保留：是**
- **继续默认暴露在 Beacon 人类面：否**
- **正确定位：internal repo-maintainer skill / dev-only governance skill**

建议：

- 从默认可见人类面中降级
- 标记为 internal / maintainer-only
- 只在 Beacon 自仓库开发场景、verify/orchestrate profile 集成场景下使用

## 5. `beacon-prototype-reconcile` 分析

## 5.1 来源

从内容和 git 提交可确认，它不是 Beacon prototype 主链自然产物，而是：

- 围绕已有前端实现 truth
- 处理 prototype/doc/code drift
- 面向 takeover / reconcile 的项目级补充 skill

并且 skill 本身多次强调：

- does **not** change Beacon core
- adds a **project-level OMX workflow** around Beacon

这说明它的本质是：

> 为特定困难场景加的外接型补强 skill。

## 5.2 用途

它解决的是这样一类问题：

- 项目已经有复杂前端实现
- Beacon prototype artifacts 与实现漂移
- 需要从代码反推 implementation truth
- 再回填 prototype/doc 才能重新进入 review/gate

这不是常规 prototype 用户都会遇到的情况，而是：

- takeover project
- stale prototype
- drift-heavy frontend
- code-first reconciliation

所以它是：

- advanced repair/reconciliation skill
- specific project rescue workflow

## 5.3 是否必要

有条件必要。

必要性属于：

- **特化场景必要**

不属于：

- **核心 workflow 普适必要**

如果 Beacon 想支持现实中的 takeover / existing UI reconciliation，这类能力是有价值的。  
但它更像：

- project plugin
- rescue workflow
- reconcile tool

而不是 Beacon prototype 正常主线的一部分。

## 5.4 对用户心智的影响

如果它和 `beacon-prototype`、`beacon-review` 一起并列出现在人类面列表里，用户会误解：

- Beacon prototype 似乎天然需要 reconcile
- prototype lifecycle 可能并不自洽
- 有一个默认需要 OMX deep review 的平行流程

这会造成三种心智伤害：

1. prototype 主路径不再清晰
2. 用户误以为 reconcile 是常规步骤
3. Beacon 看起来比实际更重、更碎

## 5.5 最终判断

`beacon-prototype-reconcile`：

- **保留：是**
- **继续默认暴露在 Beacon 人类面：否**
- **正确定位：advanced project-level rescue/reconcile skill**

建议：

- 迁到 plugin / advanced / internal-support 层
- 只在以下场景显式推荐：
  - existing frontend truth takeover
  - severe prototype drift
  - implementation-first reconciliation

## 6. 对 Beacon 人类面设计的启发

这两个 skill 暴露出一个更大的问题：

> Beacon 当前 skill 树里混入了“主流程 skill”、“support skill”、“internal maintainer skill”、“advanced rescue skill”，但没有足够清晰的人类面分层。

这正是它们影响用户心智的根因。

## 6.1 当前至少存在四类 skill

1. **Lifecycle Core Skills**
   - `beacon-prd`
   - `beacon-user-story`
   - `beacon-test-case`
   - `beacon-prototype`
   - `beacon-change`
   - `beacon-implement`
   - `beacon-qa`
   - `beacon-release`

2. **Support Core Skills**
   - `beacon-help`
   - `beacon-status`
   - `beacon-doctor`
   - `beacon-archive`

3. **Advanced / Project-Specific Skills**
   - `beacon-prototype-reconcile`
   - 其他 takeover / rescue / reconcile 型 skill

4. **Internal Maintainer Skills**
   - `beacon-iteration-governance`
   - 其他只服务 Beacon 自仓库演进的 skill

如果这些类别不分开，用户会把 3、4 类误当成 1、2 类。

## 6.2 Beacon 当前缺的不是更多 skill，而是 skill visibility governance

问题不是“为什么多了两个 skill”，而是：

- 谁默认可见
- 谁只在特定上下文可见
- 谁是 internal only
- 谁只能由 help/status/router 在特定条件下推荐

这是一条新的 boundary 需求：

> skill 存在性 与 skill 人类面可见性，必须分开治理。

## 7. 是否需要进入 v1.4.0

需要，但不是以“加更多 skill”的方式进入，而是以：

- skill visibility governance
- human-surface taxonomy
- internal vs advanced vs public routing separation

的方式进入 `v1.4.0`。

也就是说，`v1.4.0` 应补的不是：

- 把这两个 skill 并入主流程

而是：

- 正式定义它们不属于默认用户心智面

## 8. 建议处理方案

## 8.1 `beacon-iteration-governance`

- 保留源码与测试
- 标记为 maintainer/internal
- 从默认用户技能发现面降级
- 只在 Beacon 仓库开发或显式 internal mode 下出现

## 8.2 `beacon-prototype-reconcile`

- 保留为 advanced/project-level skill
- 不与 `beacon-prototype` 并列作为常规入口
- 由 `beacon-help` / `beacon-status` / `beacon-prototype` 在严重 drift 条件下按需推荐

## 8.3 v1.4.0 应新增的正式边界

- public skill surface
- support skill surface
- advanced skill surface
- internal maintainer skill surface
- skill recommendation policy
- skill discoverability policy

## 9. 最终结论

### 9.1 来源判断

- `beacon-iteration-governance` 来源于 Beacon 自仓库演进与 release-governance 需要
- `beacon-prototype-reconcile` 来源于项目级 prototype/doc/code drift reconciliation 需要

### 9.2 用途判断

- 前者是 internal repo-maintainer governance skill
- 后者是 advanced rescue / reconcile skill

### 9.3 必要性判断

- 两者都有必要性
- 但必要性都不属于默认用户主面必要

### 9.4 心智影响判断

- 两者继续默认暴露，会污染 Beacon 的极简用户心智
- 这与 `global-boundaries.md` 的方向冲突

### 9.5 高置信度建议

- 保留能力
- 降级可见性
- 通过 human-surface taxonomy 与 skill visibility governance 重新分层
