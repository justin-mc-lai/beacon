# Fix friction: package truth projection and plain-language requirement docs

## Goal

Fix two accepted friction themes in Beacon runtime behavior:

- `friction:ab595fdee485`: for feature-package-ready projects, legacy `prd/`, `user-story/`, and `qa/test-cases/` surfaces must stop being generated by default. Package truth under `docs/beacon/<version>/features/<feature>/truth.md` and package tests under `features/<feature>/tests.md` should be the default requirement read/write surface.
- `friction:eb4495db0020`: generated human-facing requirement truth must include a plain-language layer so operators can understand the outcome without decoding technical matrices.

## What I already know

- Both friction items are queued P3 improvements for `selfmedia-sync-ai`, but the root cause is in Beacon source behavior.
- `selfmedia-sync-ai` product versions such as `v0.0.12` are lower than Beacon runtime `v1.5.2`, so version-only checks like `feature_package_authoritative(version)` classify those target docs as legacy.
- The same target features already have complete package files, so `feature_package_authoritative_feature(project_root, version, feature)` correctly reports package authority for those features.
- `beacon/utils/manifest.py::compute_feature_paths()` uses version-only authority and therefore returns legacy paths for product versions such as `v0.0.12`.
- `beacon/utils/prd_bootstrap.py` writes only legacy `prd`, `user_story`, and `test_case` targets.
- `beacon/commands/user_story.py` and `beacon/commands/test_case.py` use version-only checks before resolving package truth.
- Existing package truth examples are structurally correct but too technical; generated content should separate plain-language summary, user workflow, and technical binding.

### State Model

- `legacy_default`: old behavior writes `prd/user-story/qa/test-cases`.
- `package_ready_detected`: feature package files exist even if docs version is below Beacon runtime semver.
- `package_default`: default write/read target is `features/<feature>/{truth,tests,tasks,evidence}.md`.
- `legacy_compat_requested`: caller explicitly opts into legacy split surfaces.
- Invalid transition: `package_ready_detected -> legacy_default` without explicit compatibility flag.
- Invalid transition: generated split surface claims independent requirement truth when package truth is authoritative.

## Requirements

- Default generation must not create legacy `docs/beacon/<version>/prd/<slug>.md`, `user-story/<slug>.md`, or `qa/test-cases/<slug>.md` when the feature package is ready or when package-authoritative mode is selected for that feature.
- Resolver decisions must account for feature package readiness in target projects, not only Beacon runtime semver.
- Legacy split surfaces may remain readable for old projects and may be generated only through an explicit compatibility route or flag.
- Generated package truth must include a plain-language human section with:
  - concise big-picture summary
  - user-readable workflow explanation
  - separate technical binding
- Tests must cover a target product version below `v1.5.2` with an existing feature package.
- Tests must cover that package-default bootstrap plans do not target legacy split docs.
- Tests must cover the plain-language section in generated package truth.
